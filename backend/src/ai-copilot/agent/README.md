# Unified Copilot agent (Phase 1 and Phase 2 Parts 1–3)

`POST /api/v1/ai/copilot/agent` accepts a text `message` and optional signed `conversationToken` and `conversationId`. It requires a browser session plus `X-Organization-Id` and `X-Branch-Id`. The response contains an `answer`, a new token and conversation ID, a trace ID, a completion status, and an optional server-priced draft. `/agent` and `/chat` use the same `UnifiedCopilotAgent` loop. `ReadOnlyCopilotAgent` is a compatibility export; `CopilotAgent` delegates to the same core. Existing action confirmation, execution and verification remain the execution boundary.

The production model receives five existing ERP read functions, nine conversation-state draft functions and eight business-intelligence functions through the provider's native tool calling API. The registry validates arguments and independently checks user permission and branch access on every invocation. Product and customer searches use bounded PostgreSQL RPCs through `SupabaseEntitySearchService`; prices use the active rate-list repository and authoritative pricing service. Part 3 replaces catalog-based vendor search with an indexed scoped RPC. Product detail fetches one product and at most one organization-scoped brand. No model-supplied tenant or record ID is trusted without an organization-scoped lookup.

## Phase 2A search

Also apply `20261005093000_phase2a_entity_search_result_types.sql`, the forward-only customer varchar-to-text return-contract correction. Database fixtures reproduce that production contract failure before applying the fix. The correction first initializes the existing pg_trgm library so a fresh migration connection recognizes its user-settable threshold configuration. Already-applied migrations are never edited or repaired.

Apply `20261005090000_phase2a_entity_search.sql` using the existing Supabase migration workflow before deploying the backend. `pg_trgm` lives in `extensions`; immutable expression indexes normalize matching text without editing authoritative master data. GIN trigram predicates preselect products and brands; customer search adds indexed consonant-key and exact-phone lookup. Products/customers are organization-wide masters (no branch column); every RPC still requires the exact active branch grant and the appropriate read permission through the existing P0-5 helpers. RPCs are SECURITY INVOKER, service-role only, with a fixed empty search path. Existing RLS and application authentication remain in force.

Normalization supports EBOW/ELBOW, FEM/FEMALE, PPRC/PPR-C/PPR C, PN16/PN-16, multiplication symbols and fraction spacing, case, millimeter spacing and Urdu/Arabic numerals. Numeric qualifiers must match whole normalized tokens: a different size or PN rating cannot be accepted due to name similarity. Category, product family/size/PN embedded in the name, unit, SKU and the tenant-owned brand participate. Customer location uses the existing `city` field; there is no separate address or language-alias table. Honorifics are removed, and a conservative Urdu/Latin consonant key provides cross-script candidates. Consonant collisions require clarification. Exact phone lookup is available, but phone numbers are not returned to the model.

Results contain IDs, display names, safe identifying fields, confidence and match kind, plus `resolution`, `bestCandidate`, `requiresClarification`, and `hasMore`. Confidence is a deterministic score, not a calibrated probability. A best candidate requires score >=0.90 and a >=0.10 gap to the runner-up; unique exact SKU matches take priority. Name and phonetic collisions remain ambiguous. The database returns 2–20 rows so limit=1 cannot conceal a tie; the service applies the requested display limit only after assessing ambiguity. Errors fail closed with no in-memory fuzzy fallback.

The Agent refuses pricing after a weak, ambiguous or empty search and replaces a guessed final answer with a clarification. Product ambiguity and customer ambiguity survive signed follow-up tokens. A refined, resolved search can clear ambiguity. PostgreSQL performs matching; product/customer search does not download catalog rows to Node.

Database tests execute the actual migration and P0-5 helpers in PGlite/PostgreSQL with `pg_trgm`, covering normalization, ranking, multilingual ambiguity, role/organization/branch/permission denial, RLS preservation, limits, and an EXPLAIN ANALYZE index check on 20,000 products. Run `npm test -- test/entity-search.database.test.ts src/services/entity-search.service.test.ts src/ai-copilot/agent` and the full backend check before release. The migration directory also contains verbatim SQL retrieved from production's recorded history for three migrations absent from the Phase 1 checkout; these already-applied migrations must not be replayed or repaired.

The model depends on the internal `ToolCallingAiProvider` contract. A configuration factory selects isolated Groq/OpenAI/Responses-compatible, native Gemini, or native Anthropic transports. Structured extraction and speech use the same internal boundary, with explicit separate speech-provider configuration where needed. Provider/model changes require configuration rather than changes to business orchestration. Credentials never enter conversation state. See `docs/PHASE-2D-MULTIMODAL-AGENT.md` for capability limits and verification.

The loop allows ten model iterations and twelve tool calls, with a 40-second deadline. Repeated calls, malformed calls, provider errors, and exhausted bounds return a safe fallback. Nested draft operations check cancellation before further reads and before committing state. Final answers require at least one successful tool result. Version 2 conversation state is a 30-minute, HMAC-signed token bound to user, organization, branch and conversation ID. It holds at most five product references, one customer, a brand/list choice and one draft with at most 20 stable line IDs, quantities, ERP units and discount percentages. It contains no catalog, transcript, prices or totals; up to 500 characters of prior user wording are an explicitly untrusted language hint. Strict validation and a 9,000-character token limit fail closed. Legacy signed product context can migrate into this state.

The frontend sends automatic and estimate text conversations to this agent route and retains token/identity in memory, clearing them on scope changes, other task types, reset or expiry. Conversation edits replace stale draft/confirmation controls. Media and other explicit action tasks retain the existing review flow; Part 2 adds no OCR/voice behavior.

## Phase 2B draft lifecycle

`set_task_context`, `begin_estimate_draft`, `add_draft_item`, `remove_draft_item`, `update_draft_quantity`, `update_draft_discount`, `inspect_draft`, `recalculate_draft` and `prepare_estimate` modify or read only transient signed business state. Unresolved references require clarification. Duplicate products with the same unit/list merge quantities; edits preserve draft identity and invalidate preparation. Repricing uses `DefaultEstimatePricingService`, current authorized sale rates and the existing estimate totals function. Missing rates have null amounts/totals; server-generated draft summaries replace any model-supplied totals.

`prepare_estimate` marks a complete revision ready for review. Browser-only `POST /conversation/drafts` verifies signed scope and preparation, reloads entities/rates, and persists only the existing `ai_copilot_actions` DRAFT with a server-derived idempotency key. It returns refreshed figures for display before explicit confirmation. Existing `/drafts/:id/confirm` creates the estimate through the authoritative service, applies the approved discount and independently verifies persisted records. A changed price/unit after approval blocks execution, including the estimate service's final repricing before its atomic write. Explicit recalculation invalidates preparation and advances the approval revision so the user can prepare again. Independent verification also checks the approved percentage discount. No conversational tool executes an ERP write.

State is in browser memory, bounded to 20 lines/30 minutes and may hit the encoded limit sooner with long multibyte names. Signed tokens are stateless snapshots, not durable history or a server-wide revision lock. Reset/session loss discards transient context; already persisted approval actions retain their existing explicit confirmation semantics. Part 2 added no accounting/posting changes.

## Phase 2 Part 3 business intelligence

`query_customer_ledger` reads the existing customer subledger through `copilot_customer_ledger`. Balances group the entire authorized branch ledger by currency, independently of the bounded history page. Transactions expose source dates, invoice/payment references, debit/credit and linked posted canonical journals. Latest payment is independently queried. An empty ledger has no established currency balance; a recorded zero balance remains zero. This read adapter adds no journal or posting writes.

`query_inventory` uses the existing inventory and stock-movement services with resolved product/warehouse references. Current balances are organization/warehouse scoped because those ERP tables have no branch attribution. Branch on-hand is explicitly unsupported; movement history is exact-branch scoped and uses a separate cursor. Missing balance rows are unavailable, not zero. A total is returned only for a complete first page.

`calculate_margin` obtains fresh authorized sale rates and active global PURCHASE rates from the existing pricing service. PURCHASE rate is an estimated cost basis, not realized COGS or a guessed market cost. Existing estimate totals and `DefaultEstimateProfitService` calculate discounted revenue, gross profit and margin. Missing/ambiguous rates and unit/currency incompatibility leave profit and margin unavailable. Recorded zero rates/costs remain zero; zero revenue has no margin percentage. Quantity/discount choices are signed; monetary inputs are never retained as authority.

`compare_products` resolves two to five product queries using Part 1 search, or revalidates the signed comparison set for “both”. It compares unit sale prices, active purchase unit costs, quantity/discount-adjusted gross profit and margin, or complete organization stock. Lowest price/cost or highest profit/margin/stock is selected, including ties; missing values, incomplete pages and incompatible units/currencies yield no winner. Unit sale-price and purchase-cost comparisons are undiscounted rates. Follow-up profit/margin calculations retain the chosen quantity/discount and refresh ERP values.

`lookup_vendors`, `list_payment_documents`, `prepare_customer_payment` and `prepare_vendor_payment` support safe payment review. Customer receipt and vendor payment directions are explicit; the model must request missing amount/date/method/currency/allocations rather than inventing choices. Preparations validate the scoped party, distinct allocations summing to the amount, document ownership, currency where supported and remaining balances. The vendor payment domain has no currency field, which is reported as unsupported rather than inferred.

Browser-only `POST /conversation/payments` accepts only a signed token and conversation ID, rechecks permission, branch, party and current document balances, then persists an idempotent existing approval DRAFT. The frontend displays the review and separate Prepare/Confirm controls. Only explicit `/drafts/:id/confirm` executes the existing customer/vendor domain service and requires independent persisted-record verification. Failed verification retains its execution checkpoint; retries re-read without making another payment. Scope changes and new messages remove stale UI approval controls. Stateless signed snapshots do not revoke previously issued tokens; persisted actions keep their existing confirmation semantics.

The unified model loop can sequence product resolution, pricing, inventory and margin, or ledger plus payment-document review. The server renders collected authoritative business facts so the model cannot change verified numbers or invent missing values in its final text. Urdu input receives Urdu labels; Roman Urdu and English use English numeric labels. No sentence-specific handlers, OCR/voice adapter or provider-specific engine is added. Signed state extends Part 2 with bounded vendor/comparison references and calculation/payment user choices.

Apply `20261005110000_phase2c_business_reads.sql` through the existing migration workflow before a future deployment.
